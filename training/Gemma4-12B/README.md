# Gemma 4 pedestrian-hazard training

Stride Ahead adapts `google/gemma-4-12B-it`, pinned to revision `707f0a3b8a3c7ad586ed01e27eafbad8a27dd0f7`, using rank-16 LoRA on language-attention q/k/v/o projections. The base weights and vision encoder remain frozen. The model receives images, timestamps and RF-DETR object IDs, and learns structured hazard descriptions with frame/object references and uncertainty. Application code assigns heuristic alert priority separately.

The completed prototype ran **40 optimizer steps on 155 training images and 22 validation images**, separated across 54 and six recording sessions. Its selected checkpoint had validation token loss **0.12035**. The [saved training manifest](reports/training_manifest.json) records the run and artifact hashes. Targets were generated by a source-informed teacher and filtered by an image-based critic; they remain **weak, AI-generated supervision**, not human-verified hazards. Token loss and teacher agreement do not establish real-world warning accuracy.

This directory includes its own `contract.py`, `adapter_io.py` and `worker.py` so training, export and evaluation do not depend on files outside `training/`. Data, downloaded base weights and trained checkpoints are excluded from Git. Existing trained artifacts are published on [Hugging Face](https://huggingface.co/Atlearia/Gemma_4_finetuned/tree/4627dbab33524ff1514e5a23dcf8cc73dfd49b86).

## Environment and paths

The following examples use **Linux Bash from the repository root**, Python 3.11 and a CUDA-enabled PyTorch/torchvision installation suitable for the GPU. The original full-precision LoRA run used one 80 GB H100. Use a separate environment from RF-DETR; [RF-DETR setup](../RF%20Detr/README.md) documents that environment.

```bash
python3.11 -m venv training/.venv-gemma
source training/.venv-gemma/bin/activate
# Install provider-compatible CUDA PyTorch and torchvision first.
python -m pip install -r training/Gemma4-12B/requirements.txt
python -m pip check

STRIDE_DATA="$PWD/training/data"
STRIDE_RUNS="$PWD/training/runs"
STRIDE_BASE="$PWD/training/models/gemma-4-12B-it"
mkdir -p "$STRIDE_DATA" "$STRIDE_RUNS"
export STRIDE_BASE
python -c 'import os; from huggingface_hub import snapshot_download; snapshot_download("google/gemma-4-12B-it", revision="707f0a3b8a3c7ad586ed01e27eafbad8a27dd0f7", local_dir=os.environ["STRIDE_BASE"])'
```

Access to the base model may require accepting its terms and authenticating with Hugging Face. Keep tokens in the environment or the Hugging Face login store. The base weights need approximately 24 GB; a full merged export needs another approximately 24 GB, plus temporary files and training state.

Some scripts require a future absolute deadline. Set a fresh budget immediately before each bounded stage; this example allows two hours:

```bash
STRIDE_DEADLINE="$(python -c 'from datetime import datetime, timedelta, timezone; print((datetime.now(timezone.utc) + timedelta(hours=2)).isoformat())')"
```

The relative per-stage time limit and absolute deadline both apply. Review completion reports before advancing, and use a new output directory for each rerun.

## Prepare images and detector context

The [data audit](DATA.md) describes pinned PAVE/SANPO sources, attribution and session separation. This bounded recipe prepares 300 train and 60 validation images and leaves the official evaluation split untouched:

```bash
python training/Gemma4-12B/prepare_data.py \
  --cache "$STRIDE_DATA/gemma-pave-cache" \
  --output "$STRIDE_DATA/gemma-pave-raw-source" \
  --download-media --max-train-frames 300 --max-validation-frames 60 \
  --max-test-frames 0 --max-download-bytes 2500000000 --workers 6
```

Run the next command with the **RF-DETR environment's Python**. Point `STRIDE_RF_CHECKPOINT` at a trained RF-DETR Medium checkpoint from the detector workflow or the published model artifacts:

```bash
STRIDE_RF_CHECKPOINT="$STRIDE_RUNS/medium-ood/checkpoint_best_total.pth"
training/.venv-rfdetr/bin/python training/Gemma4-12B/attach_rf_boxes.py \
  --source "$STRIDE_DATA/gemma-pave-raw-source" \
  --output "$STRIDE_DATA/gemma-pave-teacher-source" \
  --checkpoint "$STRIDE_RF_CHECKPOINT" --threshold 0.3 --batch-size 8
```

Substitute the actual RF environment path if it differs. These rows still contain source accessibility prose; they are teacher inputs, not final student targets. `data_report.json` must report `prepared` before continuing.

## Generate and filter weak hazard targets

Return to the Gemma environment. Refresh `STRIDE_DEADLINE` before these stages when needed:

```bash
python training/Gemma4-12B/generate_hazard_labels.py \
  --train "$STRIDE_DATA/gemma-pave-teacher-source/train.jsonl" \
  --validation "$STRIDE_DATA/gemma-pave-teacher-source/validation.jsonl" \
  --output "$STRIDE_DATA/gemma-hazards" --model-path "$STRIDE_BASE" \
  --deadline-utc "$STRIDE_DEADLINE" --max-seconds 1800 \
  --max-train 300 --max-validation 60

python training/Gemma4-12B/filter_hazard_labels.py \
  --train "$STRIDE_DATA/gemma-hazards/train.jsonl" \
  --validation "$STRIDE_DATA/gemma-hazards/validation.jsonl" \
  --output "$STRIDE_DATA/gemma-hazards-filtered" --model-path "$STRIDE_BASE" \
  --deadline-utc "$STRIDE_DEADLINE" --max-seconds 900
```

The student never receives the source assessment prose. The critic accepts or rejects existing targets without rewriting retained labels. Inspect accepted and rejected examples, ordinary path-edge objects, visible obstructions, empty scenes and uncertain scenes. The completed historical preparation retained 155/22 examples; a new generation run can produce different counts. [HAZARD_DATA.md](HAZARD_DATA.md) records the policies, audits and limitations.

## Validate and train

The trainer checks recording separation, decoded-image duplicates, licensing metadata, object IDs, target schema and sequence lengths. Only assistant output tokens contribute to loss. Weak labels require explicit `--allow-weak-labels`.

```bash
python training/Gemma4-12B/train.py \
  --config training/Gemma4-12B/configs/h100_hazard_lora.json \
  --train "$STRIDE_DATA/gemma-hazards-filtered/train.jsonl" \
  --validation "$STRIDE_DATA/gemma-hazards-filtered/validation.jsonl" \
  --output "$STRIDE_RUNS/gemma-hazard" --allow-weak-labels --dry-run

python training/Gemma4-12B/train.py \
  --config training/Gemma4-12B/configs/h100_hazard_lora.json \
  --train "$STRIDE_DATA/gemma-hazards-filtered/train.jsonl" \
  --validation "$STRIDE_DATA/gemma-hazards-filtered/validation.jsonl" \
  --output "$STRIDE_RUNS/gemma-hazard" --model-path "$STRIDE_BASE" \
  --allow-weak-labels --max-wall-seconds 7200 \
  --deadline-utc "$STRIDE_DEADLINE"
```

The hazard recipe uses BF16, microbatch one, gradient accumulation eight, learning rate 5e-5, LoRA rank 16/alpha 32, checkpointing, 40 optimizer steps and evaluation every 20 steps. It is a bounded prototype run. Optional `--pilot` uses 20 steps and marks the output as non-promotable; use a separate output directory for it. The alternate `h100_lora.json` configuration supports auxiliary source-QA experiments; a source-QA-only adapter is not a hazard-trained artifact.

## Evaluate and export

Refresh the deadline before evaluation. Evaluation compares the frozen base and the adapter on the same held-out examples and reports JSON validity, object grounding, teacher agreement, abstentions and generation latency:

```bash
python training/Gemma4-12B/evaluate_adapter.py \
  --validation "$STRIDE_DATA/gemma-hazards-filtered/validation.jsonl" \
  --adapter "$STRIDE_RUNS/gemma-hazard/adapter" --model "$STRIDE_BASE" \
  --output "$STRIDE_RUNS/gemma-comparison" --max-examples 12 \
  --deadline-utc "$STRIDE_DEADLINE"

python training/Gemma4-12B/export_merged.py \
  --adapter "$STRIDE_RUNS/gemma-hazard/adapter" --model-path "$STRIDE_BASE" \
  --output "$STRIDE_RUNS/gemma-merged/gemma_model.pth" --device cuda:0 \
  --deadline-utc "$STRIDE_DEADLINE"
```

Training saves a PEFT `adapter/`, a training manifest and a small adapter-only `gemma_model.pth`. The merged export is a different, full model: keep its `.pth`, matching `.json` and `gemma_model_processor/` together. Check completion fields and artifact hashes before using an output.

Optional `export_quantized.py` creates and verifies an NF4 serving copy of a completed merged checkpoint. Install `requirements-inference.txt` as well for bitsandbytes and the runtime dependencies, then use `--help` for the checkpoint, intermediate directory, validation manifest, output and deadline arguments. Quantization quality and end-to-end latency need separate evaluation.
